# 装配式装修智能体技能合集独立第三方评估与整改路线图

**评估日期**：2026-09-20  
**评估对象**：本地 Git 基线 `6a9de4599d073c6259bc4dce88eb2ff00fb69f8b`  
**评估性质**：只读制品审计、独立评审视角；不等同于真实工程项目验收、法定合规审查或大赛官方评审。  
**总体评分**：**6.2 / 10**  
**总体定位**：专业治理成熟度较高的装配式装修 AI 技能系统原型；尚未由跨环境、端到端行为和真实项目结果证据证明为成熟工程交付产品。

## 一、结论摘要

该项目的价值主张是清晰的：面向装配式装修，覆盖隔墙、墙面、吊顶、楼地面、厨卫、收纳六大系统，并提供声学计算、机电协同、验收清单、标准复核与治理能力。其“总入口路由 + 专项技能协同”架构对使用者易于理解，专业边界也较克制。

项目当前最强的能力是**治理与制品一致性**，而非已经被证明的**工程交付正确性**。现有九类守卫能够有效发现治理文件、索引引用、跨层镜像和台账结构的问题；但这些守卫不能替代宿主模型行为测试、工程专家盲评、真实项目结果和跨电脑复现。

因此，对外不宜宣称“已稳定解决真实工程问题”或“已实现自主学习”。更准确的表述是：

> 项目已形成可治理、可追溯、可持续人工迭代的专业 AI 技能体系；正在补齐端到端行为验证、跨环境可复现和真实工程验证。

## 四、已确认的关键问题

### R-01：验收清单技能与 IC-10 正式契约错接

**严重度**：阻断端到端可信性的 P0。  
**现象**：验收清单技能声明调用 IC-10，但请求字段写为“引用的标准编号、引用条文号、应用场景描述”等；IC-10 正式最小输入是“项目类型、空间类型、项目所在地、构造体系、性能需求”。

- 调用方声明：`技能仓备份/prefab-acceptance-checklist-generator/SKILL.md:313-355`
- IC-10 正式契约：`_专题_技能合集策划/interface-contracts.md:2110-2184`

**根因判断**：技能文档沿用了“条文核验/静态查表”的输入模型，却标记为“场景化标准推理”的 IC-10，接口语义与字段约束未同步。

**影响**：无法据现有文档保证“验收场景 → SRE 标准集 → 验收清单”的输入/输出能被正确消费。此问题不修复，不能对外声称主链已跑通。

**整改目标**：为验收清单技能选择唯一、可执行的调用语义：

- 若目标是“确定项目场景适用标准集”，则将调用方改为 IC-10 的正式字段；
- 若目标是“核验某标准/条文”，则改为 IC-07 或 IC-11，并同步修正技能描述；
- 任何一种选择都必须配套正向、缺字段、降级、错误路由四类行为测试。

**验收证据**：

1. 调用方示例可通过目标契约的机器校验；
2. 至少 3 个真实验收场景在目标宿主上完整运行；
3. 原始输入、路由记录、响应、清单与专家判定可复查；
4. 错接旧字段的负向样例必须稳定失败，而非静默兼容。

---

### R-02：高频多技能路由尚未契约化

**严重度**：P0。  
**现象**：总入口到墙面、吊顶、机电等高频关系仍列为“待注册”。

- 待注册清单：`_专题_技能合集策划/interface-contracts.md:2851-2877`
- 编排流程：`技能仓备份/prefab-interior-systems-orchestrator/SKILL.md:158-215`

**根因判断**：先形成了编排流程与技能文案，后续接口契约化未覆盖所有真实调用边。

**影响**：多技能协同依赖自然语言、文件名和人工理解；当技能版本、宿主能力或输出模板变化时，容易出现断链或静默误配。

**整改目标**：只为**真实高频调用边**建立最小契约，禁止为追求“全覆盖”制造无消费方的文档。每条契约至少明确：

- 发起方、接收方与版本；
- 输入字段、字段来源、缺失时行为；
- 输出字段、接收方消费位置；
- 失败/降级/转人工条件；
- 正向与负向端到端测试。

**验收证据**：冻结一条多部品任务，完整保存“总入口路由 → 专项输出 → 标准校验 → 集成校验 → 验收清单”的轨迹；任一中间件缺字段必须被阻断或降级，不能由模型猜补。

### R-03：现有门禁证明一致性，不证明专业内容与模型行为正确

**严重度**：P1。  
**事实依据**：项目已主动披露检查 8、9 的内容真值盲区和跨层同错风险。

- 检查 8 限制：`change-governance.md:470`
- 检查 9 限制：`change-governance.md:472`
- SRE 参考实现边界：`技能仓备份/shared/standards-reasoning-rules.md:9-11`

**整改目标**：将质量证据分为四类，不再用单一“门禁全绿”描述项目质量：

| 证据层 | 回答的问题 | 最低动作 |
|---|---|---|
| 制品证据 | 文件、版本、索引、契约是否一致？ | 保留现有九道门禁。 |
| 行为证据 | 宿主模型是否按技能要求执行？ | 冻结任务集、保存原始输入/输出/路由。 |
| 专业证据 | 输出是否技术正确、边界是否恰当？ | 专家盲评、条文定位、反例与转人工测试。 |
| 真实结果证据 | 是否改善项目实际工作？ | 真实试点前后对照：耗时、漏项、返工、采纳。 |

**验收证据**：四类证据必须分栏展示；任何宣传材料均不得把“制品绿灯”表述为“工程结论已验证”。

---

### R-04：跨平台、异电脑、异用户可复现性不足

**严重度**：P1。  
**现象**：README 支持多系统复制安装，但运行时文档仍有硬编码项目路径和旧运行时路径。

- 安装说明：`README.md:7-14`
- 硬编码 Windows 项目路径：`技能仓备份/prefab-governance-sync/SKILL.md:13-21, 68-72`
- 旧 `.qoderwork` 路径：`技能仓备份/shared/standards-reasoning-rules.md:3`

**影响**：不同用户、不同电脑和非 Windows 环境无法按同一文档无歧义操作；原始字节比较还可能受换行策略影响。

**整改目标**：

1. 对外技能仅使用相对路径、用户目录占位符或运行时发现机制；
2. 将本机维护路径隔离在维护文档中，不进入面向开源使用者的技能指令；
3. 明确支持矩阵：操作系统、Qoder 版本、Python/Node 依赖、可选工具与降级行为；
4. 在全新用户目录和无缓存环境中复跑冻结任务；
5. 对跨平台文本文件明确换行与编码策略，并以实际克隆环境验证，而非只在本机声明。

**验收证据**：至少两台机器、两个不同用户目录完成安装和同一任务集重跑；比较结论、依据等级、路由和转人工条件是否等效，不要求自然语言逐字相同。

---

### R-05：发布基线与公开使用者复现链不足

**严重度**：P1。  
**现象**：README 承诺发布基线打 tag，但当前基线未被任何 tag 包含；本地 `master` 相对 `origin/master` 领先 1 个提交。

- 版本策略：`README.md:61-66`
- 当前事实：评估时 `git rev-list --left-right --count HEAD...origin/master` 为 `1 0`；`git tag --contains HEAD` 无结果。

**整改目标**：在任何比赛演示、试点或公开推广前冻结“评估对象”，形成版本、包、依赖和运行证据四件套。发布动作本身须在获得明确授权后执行。

**验收证据**：

- tag 指向评估提交；
- 发布包具备哈希、安装说明和变更摘要；
- 在非开发者机器可按说明安装；
- 演示任务、测试任务与报告均标注同一版本指纹。

### R-06：自主学习尚未形成受控反馈闭环

**严重度**：P1。  
**事实依据**：项目已具备变更治理和遗留台账，但明确未在本仓实例化 agent-wiki；台账也披露“新遗留漏登记”仍依赖人工发现。

- 不实例化 agent-wiki 的裁定：`change-governance.md:443`
- 台账反向覆盖限制：`change-governance.md:462-465`

**整改目标**：先建设“受控学习”而不是让模型自行修改事实。最小闭环如下：

```text
用户反馈/专家纠错/失败任务
  → 不可变原始记录
  → 分类与风险分级
  → 责任人、到期日、处理决定
  → 技能/索引/契约的受控变更
  → 负向回归用例
  → 版本发布与效果复核
```

**硬约束**：候选知识、用户个案和未核验标准不得自动升级为事实源；涉及安全、合规、标准状态的变更必须保持既有人工复核与证据要求。

**验收证据**：至少 5 个真实反馈样本完成“原始记录—处置—回归—版本”闭环，其中至少包含 1 个错误答案或错误路由样本。

---

### R-07：公开发布面的历史暴露仍有待决风险

**严重度**：P1（开源与竞赛对外呈现风险）。  
**事实依据**：当前工作树已完成公开面脱敏整改，但历史提交、已删文件前像和部分外部 `file:///` 指针仍被登记为 PL-030，等待三择一裁定。

- 残余事项：`change-governance.md:458`

**整改目标**：在公开竞赛材料前明确选择并留痕：

- 将仓库改为私有或使用无历史的新发布路径；
- 经明确授权后重写历史；
- 接受历史保留风险，并在公开材料中限制引用范围。

此项涉及公开发布策略，不应由技术人员或智能体自行决定。

## 五、分阶段整改路线图

### 阶段 0：冻结问题与评估对象（先做，不改技能行为）

**目标**：防止边评估边改动导致证据失效。  
**优先级**：最高。  
**产出**：一份冻结清单，而不是新的技术机制。

| 动作 | 结果 | 通过条件 |
|---|---|---|
| 冻结待评估版本 | 明确 commit、运行时技能包哈希、宿主/模型版本、日期 | 所有任务记录引用同一版本指纹。 |
| 建立问题清单 | R-01 至 R-07 逐项记录状态、责任人、截止日期、证据链接 | 不将“已发现”误写为“已修复”。 |
| 明确大赛规则输入 | 收集官方赛题、资格、交付格式、评分表 | 未拿到规则前，不声称大赛准备完成。 |
| 冻结任务集设计 | 至少 30 题的任务蓝图与验收标准 | 开发者不能在执行中修改题目或评分标准。 |

### 阶段 1：先闭合端到端主链（R-01、R-02）

**目标**：证明至少一条核心用户路径不是“文档上可行”，而是“实际可运行”。

建议最小主链：

```text
用户的多部品需求
→ 总入口路由
→ 专项技能方案
→ 标准推理/条文核验
→ 跨部品协同
→ 验收清单
→ 专家复核与转人工提示
```

**实施纪律**：

1. 先以接口真值源裁定 R-01 的 IC-10/IC-07/IC-11 语义；
2. 再登记并实现真实高频调用边的最小契约；
3. 为每一条调用边补机器可验证的正向、缺字段、错字段与降级测试；
4. 在目标宿主模型实跑，而不是只运行 Python 静态测试；
5. 保存完整轨迹，供专家盲评。

**阶段通过线**：30 题任务集中，核心主链任务必须具有可复查的原始轨迹；所有高风险结论均有证据等级、条文定位或转人工说明。

### 阶段 2：补齐专业可信度（R-03）

**目标**：把“文本一致”扩展为“结果可判断”。

| 专题 | 动作 | 通过条件 |
|---|---|---|
| SRE | 建立地域、项目类型、缺资料、失效标准、外部协同等反例任务 | 输出的标准集、确定性和降级行为经专家逐题判定。 |
| ACE | 使用脱敏检测报告或可靠项目数据进行校准 | 明确误差口径、适用范围和不可用条件；不得以理论测试代替实测。 |
| 红线 | 将关键红线映射到可触发输入与预期输出 | 每条高风险红线至少有一条正向/负向行为用例。 |
| 引用 | 要求输出显示标准编号、年份、证据等级、地域/时效限制 | 缺依据时不输出确定性合规结论。 |

### 阶段 3：跨环境与发布工程化（R-04、R-05、R-07）

**目标**：让开源使用者和竞赛评委能独立获得同一能力边界。

1. 消除面向用户的绝对本机路径和旧运行时路径；
2. 提供安装前检查、依赖说明、失败降级和卸载说明；
3. 在不同用户目录和不同机器执行清洁安装；
4. 冻结 tag、发布包、哈希、变更说明和演示任务；
5. 在公开材料前完成 PL-030 的发布策略裁定。

**阶段通过线**：第三方按文档在清洁环境安装后，可复跑任务并得到等效的路由、证据等级与转人工行为。

### 阶段 4：建立受控学习闭环（R-06）

**目标**：把“人工维护”升级为“受控的持续学习”，但不放弃专业审批边界。

**最小数据模型**：反馈编号、原始输入、错误类型、影响等级、证据、责任人、到期日、处置决定、关联版本、回归用例、复核结论。

**阶段通过线**：真实失败样本能够在新版本中稳定复现旧错误、验证修复并防止回归；未核验内容不会自动成为标准事实。

### 阶段 5：竞赛呈现与现场验证

**前提**：已取得官方规则。  
**目标**：把技术能力转换为评委可感知、可复核的竞争力。

| 评委关切 | 需要展示的证据 |
|---|---|
| 创新性 | 专业知识、治理与可追溯推理如何共同降低工程咨询风险。 |
| 实用性 | 一个真实或高保真案例的前后对照：时间、漏项、返工或复核效率。 |
| 可靠性 | 失败案例、降级、转人工、标准时效处理，而非只演示成功回答。 |
| 可推广性 | 清洁安装、跨用户复跑、明确支持矩阵和发布包。 |
| 完整性 | 固定版本、任务包、原始日志、专家评分和材料清单。 |

---

## 六、避免走偏的四项约束

1. **不要继续用新增文档替代行为证据。** 新增规范、台账或设计方案不能证明模型在真实任务中正确执行。
2. **不要把自动门禁扩张成“内容正确性”宣称。** 机器校验应只承担其能判断的结构和行为。
3. **不要让模型或用户反馈自动改写专业事实。** 标准、红线、性能结论必须保留证据与人工复核链。
4. **不要在未冻结版本、未拿到竞赛规则前制作最终宣传结论。** 否则竞赛材料会失去可复核性。

## 八、最终判断

本项目不是普通的提示词集合，而是一个有专业领域意识、证据分级、变更治理和一致性守卫的技能系统。其当前短板不在“有没有更多功能”，而在“是否能拿出不依赖开发者自述的行为与结果证据”。

整改优先级应当从“继续完善文档”切换为：

> **先打通并验证一条主链，再证明专业正确性；先实现跨环境复现，再进行公开竞赛呈现；先建立受控反馈闭环，再宣称自主进化。**
