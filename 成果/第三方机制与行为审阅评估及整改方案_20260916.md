## 四、遗漏与更值得注意的点（本轮新增，按严重度降序）

### A｜生效路径与被测对象不是同一个（头号盲区）

**37 个 SRE 测试测的是 `sre_reasoner.py`，而运行时真正被执行的是 `SKILL.md` 里写给宿主模型的自然语言指令。** `sre_reasoner.py` 自述定位就是"参考实现"。这意味着：

- 门禁全绿只证明**参考实现**对，不证明宿主模型按 SKILL.md 走时会走出同一条推理；
- rules.md 与代码已在 DB/DBJ 层级上分歧（§二），说明"文字判据 ↔ 代码判据"漂移在本项目**已经发生过**；
- **推论（对 P0 是决定性的）**：§三 的 8 条若只改 Python 而不同步改 `SKILL.md` / `reference.md` 的自然语言判据，用户实际得到的答案不变 — 修的是不在生效路径上的东西。

这正是"条文存在 ≠ 机制生效"在本项目的最深一层：不只是条文没有承担者，而是**门禁保护的承担者与实际承担者不是同一个**。

### B｜178 条红线只做到数量守恒，未做到行为守恒

门禁与 `sr_ic07_compliance_test.py` 查的是计数一致（178、15/15）与**文档锚定**（文字是否存在），没有任何检查问"这条红线在什么输入下触发、触发后输出什么"。因此 178 条红线在当前证据下**可能是 178 条陈述句**。红线是本项目对外承诺的安全底线，这个缺口比 §三 任何单条都重。

### C｜文档通胀已达空转预警区

按实测：过程文档 = `记录/` 43 + `文档/` 9 = **52**；成果 = **8**（含 1 件 README）。比值 **6.5 : 1**。

借用你自己体系内的判据口径（`compliance-audit` §可用检查项：**过程文档数 / 成果文件数 > 3 即空转预警**），本项目为阈值的 **2.2 倍**。
> 诚实边界：本仓无 `_工具/workspace_health.py`，此为**借用该判据口径的手工计算**，非该工具实测结论。

同期观察：门禁项 171→195、`validate_governance.py` 增至 1470 行、CG 编号已至 -010，而 `成果/` 净增有限。**机制在单调递增，交付物没有同步递增** — 这是"分析正确性不等于执行可靠性"的典型形态。

### D｜Harness 从未递减

agent-wiki 明文要求"每次 Lint 审视：哪些校验规则已不再触发？哪些步骤模型已内化？删掉它"，并对新增机制同样施加递减约束。**本项目至今未删除过任何门禁项或治理条款，只增不减。** 门禁 195 项中有多少是长期恒真的空跑，当前无人知道 — 而恒真断言等于不设防（这条你已在别处确立过：摘档后的守卫须仍能失败）。建议把"恒真项识别"本身做成一次性核查，而非新增一条常驻检查。

> **R1 补**：新版已把递减从原则改为**可证伪触发条件**——"质量过滤器与蒸馏回测若连续 3 次 Lint 未产生真实信号（未滤掉常识、未触发降级或边界补注），应审视简化或删除"。本项目可直接照此立判据：**某门禁项连续 3 次运行未产生任何 FAIL/WARN 且无反向注入自证，即列入删除审议**。这把本项从"呼吁"变成可执行动作（对应 P2-20）。

### E｜真值面缺口约六成，且以确定性口径输出

`standards-index.md` 中序号 11-13、15、18-30、32-54、57-59 仍为"待核验"，粗估 **40+ / 69 ≈ 58% 主表标准未回读官方原文**（区间估算，非精确计数）。而 SRE 对这些标准照样输出"现行有效"，因为它只读`状态`列、不读`核验状态`列（§三·7）。

**即：当前约六成标准引用属于"未经官方核验但以确定性口径对外输出"，直接违反索引自身明文规则。** 对强制性国标而言这是责任级风险，不是技术债。

> **R1 补**：新版维度 10 提供了本项**现成的解法机制**，无需自行设计——其核心是"一条合格回测都没有时回落卡名日期，使『从未回测』= 满窗到期而非免检"。同构移植即"从未官方核验 = 已超期，不得输出确定性状态"，并配"补核验与降确定性等价出口"使积压不阻塞业务。逐条对位见 §6.2，落地见 P1-9/10。这也是本报告修订 §六 结论的直接原因。

### F｜唯一事实源在单机，且备份工具会删范围外文件

L2 运行时 SOT 在本地 `~/.qoder/skills/`；异地副本靠**人工触发** `sync_skill_backup.py` + **人工 commit**。而该脚本：
- 范围是固定的"15 技能目录 + 根治理文件 + shared 7 文件"，**落在 `技能仓备份/` 内但不属该范围的文件会被当差异删除**（`_pre20260916CG009` 首跑即被删，实测"移除 1"）；
- `sync()` 末尾恒 `return 0`，`--check` 有差异也 exit 0 — **不能只看返回码判一致**；
- 不排除 `__pycache__/*.pyc`。

当前 `git status` 另显示 `change-governance.md` 的 L1 与备份两份均已改但**未提交** — 未提交即异地副本不存在。这是可接受的中间态，但要标出。

### G｜ACE 的精度是自证的，责任边界需前置

90 个测试中有若干是硬编码常量关系与"文档含 ±2-3 dB"字面检查，**不构成外部精度验证**。隔声估算若无检测报告标定，实际偏差可能远超 ±3 dB，而隔声不达标的工程后果是返工。
**要求**：ACE 输出必须始终强制携带"估算值、须以检测报告为准"标注，且**不得进入验收判据**。这是责任问题，优先于技术问题。

### H｜没有失败案例库 — 自我进化最高价值的语料位是空的

项目有红线（禁止什么）、有标准（依据什么），**没有"曾经答错什么"**。而错误案例恰是密度最高的进化语料。这个空位与 agent-wiki 的 `采集经验.md`（踩坑教训结构化）严丝合缝 — 见 §六。

### 6.1 结论（R1）

**适用，但必须分轨，且顺序有硬约束：先接消费端，再开维度。**

**保留并强化的部分** —— 两者仍是**正交的两个筛子**：

| | agent-wiki | 本项目 |
|---|---|---|
| 入库判据 | 排他性 + 生成力（**对行为有用**） | S1 = 官方发布 + 官方原文核验（**具权威效力**） |
| 失败后果 | 规则没用，删掉即可 | 引用无效，可能导致工程不合规 |

新版实测把这条从推理升级为**证据**：真实实例 32 张蒸馏卡中 **25 张（78%）`pointers=none`，即无任何落地载体**，🟢 仅 3 张。也就是说，在方法论自己的家里，**蒸馏产出不是瓶颈，落地消费才是**。本项目形状完全相同：195 项门禁 PASS，却有 8 个输出断点（§三）。**若不分轨直接套用，导入的会是同一套"产文不产行为"的失效形态**，外加一层"有用被误读为合规"的责任风险。

**修订的部分** —— 原文"agent-wiki 绝不介入合规轨"**过于绝对，予以更正**：

> **判据不介入，账本机制移植。**
> S1（官方双要素）仍归 SSCV，价值两问（排他性/生成力）永不得作为合规判据；
> 但**维度 10 的到期账本纪律应当移植进合规轨**，因为它正是本项目 §三·7 与 §四·E 缺的那个机制。

### 6.2 维度 10 → 合规轨时效账本（本次最有价值的移植）

本项目现状：主表 69 条中约 58% 为"待核验"（从未回读官方原文），而 SRE 照样输出"现行有效"——**"从未核验"当前被当作"免检"处理**。

维度 10 的四条纪律逐条对位，且都是本项目自己写不出来但急需的：

| 维度 10 纪律（新版原文口径） | 移植到合规轨 |
|---|---|
| **从未回测 = 满窗到期，而非免检** | 从未核验的标准 → 按**已超期**处理，不得输出确定性状态。直接封堵 §四·E 的 58% 缺口 |
| **到期后「补回测」与「降级」是等价出口** | 「补官方核验」与「降低输出确定性」等价 —— 使积压不阻塞业务，同时不假装合规。这正是 P1-10 的合法性来源 |
| **锚点由机器算，卡内散文自报不作数**（原文："散文不会自己过期，实测曾因此把到期卡豁免成永久免检"） | 到期必须由 `validate_governance.py` 从`官方核验日期`算，**不得由索引正文的"建议每季度核验"承载**。当前正是散文承载 |
| **假锚点须留痕不得抹除** | 被证伪的标准版本/替代关系保留原文并就地标注，不改写历史 |

移植时**必须改常量**：`GREEN_BACKTEST_WINDOW_DAYS = 14` 对标准核验无意义，应按索引明文分档为 **强制性国标 92 天 / 其余 183 天**（同时修 §三·7 的单档缺陷）。

### 6.3 维度 11 → 门禁架构处方（比"加一项门禁"更根本）

维度 11 的设计是**存在性与真伪分离**："只裁有无与非空，不裁真伪——真伪归判断层回测抽查"；配套"不可判记 WARN，不静默算通过"、"SKIP 必须给理由"。

这正是 §三 共性根因的解药。本项目现有 195 项门禁**全部是存在性/一致性检查，却承担着"内容正确"的心理预期**。正确拆法是：

```
机检层（便宜、全量、恒跑）   → 存在性：字段有无、枚举合法、哈希相等、日期到期
判断层（贵、抽样、周期跑）   → 真伪：给定场景输出的标准集是否正确、红线是否真会触发
两层之间不得互相冒充；机检零 ERROR 不得被读作内容正确
```

对应到本项目：§四·B（178 条红线只做数量守恒）应落在**判断层抽样**，而非再加一条机检计数；§三 的 8 个断点应落在机检层的**场景级期望值断言**（给定输入 → 断言输出标准集），这是当前完全缺失的一类检查。

### 6.4 采用顺序的硬约束（R1 新增，源自实测代价）

新版把维度 10/11 移出采用门控，意味着**一旦采用即无条件生效**。真实实例给出了采用的即时代价：

- **68 条 WARN 全部是维度 11**，横跨 2026-08-17 → 09-16，即**整月零归因登记**；
- **4 条 ERROR 全部是维度 8**：台账记 `DOC` 而注入面实况 `WARM`。

这不是治具坏了——治具 41 测试通过、样本库 0 问题、维度 10 对 3 张 🟢 卡真实通过（合格锚点 2026-09-16、`落地自查` 0 次）。**这是被检查的库欠账，且欠账只有在维度 11 上线后才可见。** 对本项目的含义：

> **顺序必须是"先把归因登记面接上，再开维度 11"**，否则采用当日即得到一堵 WARN 墙。
> 而 WARN 墙被忽略，正是本项目已确立的失效态（AGENTS.md 明记 2 条 WARN 长期挂在基线里）。
> 具体做法：治具的 `ATTRIBUTION_FIELD_SINCE` **必须设为启用日期**（当前为 `""` 即全量追溯），否则 43 件历史 `记录/` 会一次性全部转 WARN——实例的 68 条已实证此代价。

### 6.5 融合设计（分轨 + 单向交汇，R1 微调）

```
轨道 A｜合规轨（已存在，SSCV 管判据；R1 起借用维度 10 的到期账本机制）
  标准原文 → SSCV S1 核验 → standards-index 状态 → SRE 消费
  判据 = 官方性（不可被价值两问取代）
  账本 = 到期由机器算，从未核验即超期，补核验与降确定性等价出口

轨道 B｜经验轨（新建，用 agent-wiki 方法论）
  现场问题 / 失败案例 / 产品实测数据 / 厂家技术资料 / 行业讨论
    → 采集 → 蒸馏为决策规则 → 落入 SKILL.md / reference.md 判断条款 → 效果回流
  判据 = 排他性 + 生成力 + 适用边界
  产物**永久标注"经验级"，不得冒充标准依据**

交汇点（唯一，单向）
  轨道 B 发现经验规则与标准冲突 → 触发轨道 A 的 SSCV 核验工单
  （即「矛盾处理协议」的本地落地：不悄悄覆盖、不强行调和、不假装不存在）
```

命名空间必须隔离：**经验轨标记改用 E1/E2/E3 或强制前缀"经验级"，不复用 🟢/🟡/🔵**，避免与 S1 混读。

**三个天然接口（成本低于预想）**：
1. **缺口预登记已自动产出** —— agent-wiki 要人工填的"无命中 + 缺哪类规则"，本项目 SRE `未覆盖领域`、索引`待核验`、SSCV`未决事项`**已在自动产出**，只是没被接住。汇成工单表即可，不需新采集工程。
2. **角色分离已天然成立** —— Planner/Generator/Evaluator 对应 人 / 各技能 / SSCV+QA+门禁；"生成方不得自评"本项目已在做。
3. **失败案例库对位空位** —— `采集经验.md` 正好填 §四·遗漏 H。

**注入面映射（并由此暴露一个隐性天花板）**：

| agent-wiki | 本项目对应物 |
|---|---|
| 热层（常驻注入的 `MEMORY.md`） | **各技能 `SKILL.md` + `shared/` 治理文件**（每次调用必读） |
| 温层（按需读取的蒸馏卡正文） | `reference.md` / `examples.md` |
| 冷层（tombstone + 操作日志） | `记录/` + CG 登记行 |
| `hot_layer_cap` | **`SKILL.md` 的篇幅预算** |

最后一行是本次审阅浮现的**新洞察**：`SKILL.md` 越长，宿主模型漏读既有规则的概率越高，而项目从未把它当作**受管的稀缺资源**。这意味着"往 SKILL.md 堆规则"有天花板：**新规则挤占既有规则的注意力，表现为已有红线静默失效，且不会被任何现有门禁发现**（门禁只查文字在不在，不查模型读到没读到）。往后每加一条 SKILL.md 规则，应同时回答"挤掉了谁"。

### 6.6 明确不适用的部分（诚实剔除，不假装通用）

- **来源白名单 URL 校验（维度 6）**：标准原文是出版物/PDF，多数需购买，非 URL 可达 → 对轨道 A 无意义（实例亦因白名单未配置而 SKIP）。
- **采集引擎抽象（AutoCLI / WebFetch）**：轨道 A 大量输入无法自动采集 → 只对轨道 B 有效。
- **`hot_layer_cap` 按条目数计**：应改为篇幅/注意力预算（§6.5），照搬条目数会失真。
- **归因率设为目标**：新版双重禁令（🟢 产出率与归因率均不得设数值目标）→ 本项目同样只作观察量，`无命中` 是合法值。
- **三色标记直接复用**：见 §6.5 命名空间隔离。

### 6.8 跨项目结构性教训（R1 新增，R2 扩为三处实例：派生副本缺强制刷新触发点）

实例的 4 个 ERROR 全部源于**机器生成的台账未重刷**——台账由 `--refresh-landing-ledger` 生成且"禁手编"，但**"禁手编"防不住"忘了重刷"**。

本项目有同形前例：`技能仓备份/同步说明.md` 同为机器生成清单，AGENTS.md 明记其曾"失准、待重跑"（CG-20260829-001 ⑤），到 CG-20260916-006 ④ 才闭合。

**R2 补入第三处**：agent-wiki 自身的 `.github/workflows/lint.yml`，job 名与注释仍写"七维治具回归 / 七维各造一次违规"，而 SKILL.md/README/validate.py 已是十一维、测试实际 41 例覆盖十一维。**这是手抄型派生副本**（维度数被抄进 CI 标签），与上两处机器生成清单同族：副本不会自己跟上源。

**三处实例、同一失效族：派生副本（无论机器生成还是手抄）缺少强制刷新触发点，靠人记得。** 按"加固优先结构性隔离而非协议式约定"的判据（约束失效时若靠"有人记得"才发现即不可选），修法不是写更醒目的提示，而是把刷新挂到必经动作上：

- 本项目：`sync_skill_backup.py` 的写盘分支已会重生成 `同步说明.md`，缺的是**"commit 前必须跑过同步"的机检**——可由 `validate_governance.py` 检查 6 顺带比对 `同步说明.md` 的清单与 `技能仓备份/` 实况（当前检查 6 明文**不读**该清单以避免自指，故需改为"只比文件集合与哈希、不以其为基准"，仍不构成自指）。
- 采用轨道 B 后：`落地台账.md` 的重刷挂到 CG 收尾步骤，而非 Lint 时临时想起。

> 边界声明：第三处实例（agent-wiki 的 CI 标签）属 `D:\Qoder-Files\agent-wiki` 仓自身，**本报告只记录、不代改**（修改仅限本工作区）。记它的意义在于：连以"治具裁定"为立身之本的方法论仓，其 CI 标签也会手抄漂移——这证明该失效族与作者水平无关，只与"副本有无强制刷新触发点"有关。

### 6.9 落地最小集（R1：成本下调，因治具可直接复用）

原估"需自建治具"，实测治具已存在且通过 41 测试，故：

1. **不新建目录树**，复用现有 `记录/`；新增一份 `知识库/落地台账.md`，由脚本生成、禁手编。
2. **复用或参照 `agent-wiki/scripts/validate.py`**，改两处常量：`GREEN_BACKTEST_WINDOW_DAYS` → 强制国标 92 / 其余 183 分档；`ATTRIBUTION_FIELD_SINCE` → 设启用日期，不做全量追溯。
3. **缺口工单表**：`{缺口类型, 触发场景, 标准编号, 责任人, 到期日, 状态}`，数据源 = §6.5 三处既有输出。
4. **归因字段**进 CG 登记行或 `记录/` 报告：`命中: 命中{规则}——改变了{哪个决策} / 无命中（缺哪类规则） / 不适用+原因`。判据：**说不出被改变的具体决策 = 未命中**。
5. **先接 3、4，再开维度 11**（§6.4 顺序约束）；维度 10 可与 P1-9/10 同批落地。
6. 引入 Harness 递减核查，触发条件采用新版可证伪表述（连续 3 次体检未产生真实信号即审视删除），对应遗漏 D。

## 八、总评

**本项目的治理机制质量明显高于其业务真值质量。**

门禁能证明 121 个文件字节全等，却不能证明一条标准引用是对的；索引写着核验分档规则，却没有代码读它；37 个测试保护着一个自述为"参考实现"的文件，而真正被宿主模型执行的是旁边那份 SKILL.md。

下一阶段的投入应从**"加机制"转向"接消费端"**：让已经写出来的规则有承担者，让已经打印出来的缺口有到期日，让至少一次真实工程结果进来当判据。

agent-wiki 该融，但**融的方式在 R1 复核后被修正**（§六）：

- **经验轨用它的判据** —— 补"从错误和现场中长出规则"这条本项目缺失的能力（§四·H 的失败案例库）；
- **合规轨借它的账本机制，不借它的判据** —— 维度 10 的"从未核验即超期而非免检 + 降级与补核验等价出口"正是 §四·E 那 58% 缺口缺的东西；但 S1 官方双要素仍归 SSCV，**价值两问永不得充当合规判据**；
- **顺序有硬约束** —— 先接消费端与归因登记面，再开维度 11，否则采用当日即得 WARN 墙。

最强的一条论据来自它自己的实例：32 张蒸馏卡中 **25 张无任何落地载体**，整月零归因登记，治具判 FAIL。**方法论的瓶颈从来不在"能不能蒸馏出规则"，而在"蒸馏出的规则有没有被消费"** —— 这与本项目 195 项 PASS 却有 8 个输出断点是同一个病。所以融合的真正收益不是多一套采集流程，而是**多一台能把"规则没生效"变成可机算数字的机器**。这台机器已经写好、通过 41 项测试、并且刚刚在它自己家里抓出了欠账。
