## 一、智能体现状分析

### 1.1 整体架构概况

装配式装修智能体采用 **编排器 + 领域技能 + 共享服务引擎** 的三层架构，是当前国内装配式装修垂直领域中已知规模最大的 Prompt 工程体系。

| 维度 | 数据 |
|------|------|
| 技能总数 | 16 个（7 领域技能 + 2 共享引擎 + 7 辅助/工具技能） |
| 治理文件 | 6 个核心文件，合计 4,825 行 |
| 接口契约 | 10 个正式注册（IC-01 ~ IC-10），8 个已具备 JSON Schema |
| 红线总量 | 90 条，覆盖 8 个技能 |
| 规范索引 | 67 条现行标准（14 强制 + 24 推荐 + 5 图集 + 20 产品 + 4 其他） |
| 历史审计报告 | 23 份，跨度 2026-05-31 至 2026-08-08 |
| 版本发布 | GitHub v1.0.0（2026-08-07），运行时 SOT 比公开仓更新 |

### 1.3 成熟度分级

按认知架构和工程化程度，16 个技能可分为三个成熟度梯队：

**第一梯队——v2 决策方法论 + 验证引擎（PW / CL / FL / WS）**

这四个技能共享同一套认知架构：三层知识模型（A 原则红线 / B 方法论 / C 案例）、多文件结构（SKILL.md + reference.md + examples.md）、B2 验证协议（Step 0 SRE → Step 5 输出装配）、正式 IC 契约、P0/P1/P2 分级红线、降级策略和最小保留集。每个技能均经过 2~4 轮 QA 测试，红线基线全部闭合（PW 23/23、FL 21/21、CL 17/17）。

**第二梯队——v1 技术顾问（BK / ST / MI）**

仍使用单文件主导结构，无 SRE/ACE 集成，红线采用无编号要点列表，未升级到 v2 验证协议。

**第三梯队——共享引擎与工具技能（ACE / SRE / OR / SR / ACL / QA / GS / SSCV / WF / ME）**

各有明确职责，成熟度参差不齐：ACE 高度成熟（71 项回归测试全绿），SRE 已发布但运行时集成尚未完成，OR 编排器自身未经功能测试。

## 二、问题缺陷梳理

### 2.1 P0 级——结构性风险（影响系统可靠性）

#### 2.1.1 领域技能成熟度断层

BK（厨卫）、ST（收纳）、MI（机电集成）三个领域技能仍停留在 v1 架构，缺少 SRE/ACE 集成、P0/P1/P2 分级红线、多文件知识分层和降级策略。这三个技能处理的建筑系统（防水排水、柜体安装、管线综合）在工程后果上与隔墙/楼地面/吊顶同等关键——厨卫防水失败导致渗漏索赔，机电协调失败导致返工。

在编排器多组件协同场景下，PW/CL/FL/WS 的输出经过 B2 验证协议和 SRE 规范推理双重校验，而 BK/ST/MI 的输出仅依赖单步顾问式判断，形成了 **不均匀的质量表面**。

#### 2.1.2 编排器（OR）自身未经验证

OR 是整个系统的入口和路由中枢，但从未接受过任何功能测试：路由准确性、多技能并行调度、全局约束传递、异常处理均未被验证。S1-2 已将其红线在 SKILL.md 中就地定义（OR-R-P0-1 ~ OR-R-P1-3 共 8 条），并在 redlines-registry.md 中同步注册，消除了悬空依赖；但运行时行为仍需补测。

#### 2.1.3 静态测试与运行时行为的鸿沟

所有 23 份历史审计报告均为文件级静态分析（读取 Markdown 文件并核验内容），没有任何一份报告测试过实际 LLM 推理时的运行时行为。这意味着：红线在文件中的"文字表述"被验证了，但 LLM 在实际对话中是否真正"遵守"这些红线，完全是未知数。这是整个质量保证体系中最根本的方法论缺口。

### 2.2 P1 级——工程质量问题（影响维护性和扩展性）

#### 2.2.1 治理文件三重维护负担

变更事件在三个地方分别记录：change-governance.md 主日志（27 条）、各治理文件各自的变更日志（interface-contracts 14 条、redlines-registry 12 条等）、项目根 CHANGELOG.md（仅 1 条）。三份日志粒度不同、更新节奏不同，已多次出现漂移（CG-20260612-006、CG-20260808-025）。

#### 2.2.2 interface-contracts.md 体量大且持续膨胀

当前 2,474 行，其中 JSON Schema 约占 1,500 行。随着 IC-01、IC-04 补完 Schema 和更多技能接入，文件将继续增长。单文件承载所有契约的定义、Schema、降级策略和变更日志，维护风险集中。

#### 2.2.3 技能标识符映射双份维护

14 个技能的标识符映射表同时存在于 interface-contracts.md（§5）和 redlines-registry.md（§2），两个文件均声明必须保持同步。虽然截至目前变更日志显示两者一致，但这种双份维护是漂移的温床。

#### 2.2.4 README 和 CHANGELOG 数据陈旧

README 声明"59 条现行标准"，实际为 67 条（S1-4 已修正）。CHANGELOG 已补充 v1.1.0 发布记录，但 27 条变更治理记录和 14 个接口契约版本的细粒度日志仍未完全反映。

#### 2.2.5 部分红线缺乏分级和编号

ME（材料专家）有 7 条扁平"禁止行为"无 P0/P1/P2 分级，SR（标准复核）5 条同样无分级，QA（测试技能）0 条红线。SR 在编排器工作流中承担独立方案校验角色，其红线无分级意味着冲突仲裁规则未定义。

#### 2.2.6 IC-03 Schema 已完成迁移（S1-3 已复核）

IC-03（PW→ACE 空气声隔声）的 JSON Schema 已迁移到 ACE-IN/ACE-OUT 嵌套结构，顶层 required 与 IC-08/IC-09 一致（请求：`调用方标识`、`构造描述`；响应：`计算结果`、`风险识别`、`关键假设说明`、`适用边界声明`、`超出范围提示`），字段歧义已消除。报告中"旧版未迁移"论断过期。

### 2.3 P2 级——改进空间（影响专业性和用户体验）

#### 2.3.1 WS（墙面系统）SKILL.md 过长

600 行为全合集最长，且内部编号存在不一致（全局映射表使用 "WS-P0-1" 而非 "WS-R-P0-1"），补充标准章节约 60 行与 reference.md 存在重复。

#### 2.3.2 术语表更新滞后

glossary.md 缺少撞击声术语（L'nT,w / Ln,w / ΔL，已在 CG-20260807-018 标记但未补充），GB/T 19889.1-2026 替代旧版的更新未反映。

#### 2.3.3 非单调编号

standards-index.md 采用"零波纹追加"策略，导致条目 60~62 物理位置排在条目 43~47 之前，对读者造成困惑。

#### 2.3.4 散落的已知偏差项

至少 5 个"留档"观察项散落在 change-governance.md 变更日志条目中（如 CG-20260808-025 OBS-3 声学强制场景风险、CG-20260808-026 WARN-1 IC-10 字段约束偏差），未集中管理为技术债务清单。

## 四、风险评估

### 4.1 高风险

| 风险 | 触发条件 | 潜在影响 | 缓解现状 |
|------|----------|----------|----------|
| **运行时红线失效** | LLM 在实际对话中未遵守文件中定义的红线约束 | 输出可能包含违反规范的建议（如将耐火隔墙误判为非承重隔墙），导致工程安全风险 | 当前仅有静态文件验证，无运行时监控 |
| **编排器路由错误** | OR 将用户请求路由到错误的技能，或遗漏应调用的技能 | 多组件方案不完整，可能遗漏关键系统（如做了隔墙方案但忘了吊顶隔声贡献） | OR 从未接受功能测试 |
| **治理漂移累积** | 三层同步（策划仓 → 运行时 SOT → 只读镜像）在高频修改中累积偏差 | 不同运行实例使用的治理文件版本不一致，导致输出不可复现 | prefab-governance-sync 技能可管理同步，但漂移已多次发生 |

### 4.2 中风险

| 风险 | 触发条件 | 潜在影响 | 缓解现状 |
|------|----------|----------|----------|
| **BK/ST/MI 质量洼地** | 用户咨询涉及厨卫或机电集成等 P0 后果场景 | 这些技能缺少 SRE 集成和降级策略，输出可能引用过时标准或遗漏关键校验 | v1 架构仍具备基本专业能力 |
| **context 溢出** | 多组件方案需要依次加载 PW+FL+CL+WS 的全套文件 | SKILL.md 合计约 2,000 行 + reference.md 合计约 8,000+ 行，可能超出 LLM context 窗口 | OR 使用文件式交接（方案提交表）缓解 |
| **interface-contracts.md 单点故障** | 该文件损坏或出现内部不一致 | 10 个接口契约全部受影响，跨技能通信中断 | 有 JSON Schema 校验机制，但仅限 8/10 个契约 |

### 4.3 低风险

| 风险 | 触发条件 | 潜在影响 |
|------|----------|----------|
| 术语漂移 | glossary.md 更新不及时 | 跨技能术语不一致，如 Rw 与 Rw,lab 混用 |
| 标准版本滞后 | 新国标发布后 standards-index 未及时更新 | 引用废止标准 |
| 编号混乱加剧 | standards-index 非单调编号 + 多文件重编号 | 新贡献者难以理解文件结构 |

## 五、发展前景

### 5.1 当前定位

这是国内装配式装修垂直领域中 **已知最系统化的 Prompt 工程体系**。其治理架构的复杂度（6 治理文件、10 接口契约、90 红线、三角色验证模式）在同类项目中罕见。第一梯队的 4 个领域技能（PW/CL/FL/WS）和 ACE 声学引擎已达到生产可用水平。

### 5.2 核心瓶颈

项目当前面临的核心矛盾是：**治理基础设施已高度成熟，但多数产品尚未通过生产线。** 治理文件合计 4,825 行、变更日志 27 条、接口契约 14 个版本——这些都是"生产线"；而 16 个技能中仅 4 个完成了完整 QA 流程、3 个尚未升级到 v2 架构——这些是"产品"。

### 5.3 发展建议

**阶段一（Q3 2026）——填平质量洼地**

优先完成 BK 升级（防水后果严重），然后 ST 和 MI。同步引入运行时红线验证机制，这是质量保证体系从"文件级"跃迁到"行为级"的关键一步。

**阶段二（Q4 2026）——系统级验证**

完成全 7 领域技能的 v2 统一后，设计端到端集成测试场景。目标是验证 OR 编排器在真实多组件方案中的协同能力——这是从"单技能可用"到"系统可信"的关键跨越。

**阶段三（2027）——生态扩展**

在核心系统稳定后，考虑向外扩展：与 BIM 工具的接口适配、与飞书多维表格的项目管理集成、面向终端用户的轻量化交互界面。当前架构的接口契约设计已为这些扩展预留了可能性。

### 5.4 总体评价

装配式装修智能体在架构设计、领域知识深度和质量治理体系方面展现出极高的专业水准。其最大的亮点不是任何单一技能的深度，而是 **治理基础设施的系统性**——变更治理、接口契约、红线注册、规范推理、三角色验证形成了一个闭环的质量保证框架。这个框架一旦全面覆盖到所有技能并经过运行时验证，将构成真正的竞争壁垒。

当前的主要风险不在技术能力，而在 **工程完整度**——9 个技能未经 QA 测试、编排器零覆盖、运行时行为未验证。这些不是"能力缺陷"而是"交付缺口"，通过系统化的补测和升级可以逐步闭合。

**一句话总结：生产线已就绪，产品需要过线。**
