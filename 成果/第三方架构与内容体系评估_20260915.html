01 / VERDICT

保留本项目骨架，吸收知识组织与证据交付方法

不建议整体替换本项目，也不建议把两套第三方内容直接合并进运行时。更有效的方向是：先修复已复现的执行断点，再用小范围、可追溯的结构化知识包补充现有技能。

优先级：实际错误与降级失效 → 判据、解释卡、证据的可靠关联 → 按场景补齐知识深度 → 并行启动“演进检测”（到期 / 死链 / 缺口信号，低成本、不依赖外部原文，见 07 演进机制）→ 最后才是自动采集、桌面化和大规模平台改造；裁定端始终过门。

三套系统解决的问题不同：本项目重在专业分工、计算与协同；WorkBuddy 重在一个专家入口背后的判据、误读卡和取证纪律；Codex 重在标准内容的整理与可导入交付。架构应按使用场景评判，不能按智能体数量、层级数量、卡片数量或通过断言数排总分。

本报告不设未经标定的“成熟度分数”，不把历史自评当独立证据。对当前文档内部矛盾、代码运行缺陷、历史整改记录及尚未复核的标准数值分别下结论。

分开管理六件事，避免一个等级包办一切

建议的数据设计原则是：分别表达法律效力、标准生命周期、具体条文适用性、来源/原件身份、抽取与校勘状态、核验时效。扫描/原生、官方/转载、发布/生效、全文/部分条文废止，不能揉成一个高低分。来源渠道不必然改变条文内容，但仍影响真实性核验路径；取得文本也不自动证明现行有效。

最小试点字段可复用现有概念：完整标准号与年份、条文号、项目/地区/系统/对象、评价量/运算符/数值/单位、适用条件与例外、规范语气、证据 ID/哈希/物理页、核验日期/复核时间、条文替代关系、知识类型与允许用途。它是本次建议的数据契约，不是已实现功能，也不是要求一次性建成全库。

受控原件与状态核验 → 已复核判据 → 解释卡 → 现有专业技能消费 → 标准复核 → 带证据和限制的用户输出

模型可以辅助检索、提炼和发现矛盾，但不能给自己生成的判据签发“正确性通行证”。结构、数值与方向可用确定性检查；原文对应与适用性仍需独立复核。关闭增强链后应能回到原有技能与“待核验”路径，不得把未过门的摘要当运行时事实。

07 / EVOLUTION LOOP

从“投喂知识”转向“暴露无知＋低成本填补”

前期靠本地知识库投喂来完善专业内容，瓶颈在于：用户认知与库覆盖都有限，既跟不上规范迭代，也覆盖不了真实工程的长尾场景。出路不是让模型自己写规范、再自证正确——那会直接撞上本项目红线（LLM 不作正确性闸门、运行时只消费已过门产物）。真正的杠杆是让系统的“无知”可见、可触发、且填补成本极低。

角色转换：把用户从“知识作者”退到“核验批准者”。作者受认知上限约束、不可扩展；批准只需判断“这条证据够不够”，可扩展。系统负责稳定说出“我没有核验依据”，用户负责裁定要不要补、补得对不对。这才是对抗“用户认知有限”的正解，而不是把 AI 放大了去自写规范。

先把两个被混在一起的演进问题分开

时效演进

标准被替代、复核到期。这是监控 / 触发问题：检测端可几乎全自动（确定性的日期与版本比较），但“宣布现行有效”这个动作必须留在过门侧，不由模型自签。

场景复杂性

新项目、不同用户的长尾，不可能靠预先枚举更多知识解决。靠两件事：①诚实降级——无依据时稳定输出“待核验 / 未覆盖”，绝不编数；②把真实提问转成缺口信号——命中未覆盖的问题，就是下一批该补什么的依据。

合流点

两者都指向同一机制：把“该喂什么”从用户脑子转移到系统运行日志。缺口信号＋到期信号＝一张自动排序的待核清单，用户只批准、不预先穷举。

关键发现：本项目已有生命周期原语，只是没接到生效路径

这不是从零设计。standards-index.md §1.1 / §1.1A 已经定义了完整的时效纪律：标准状态五态（现行有效 / 即将实施 / 过渡期 / 已废止 / 被部分替代）、核验状态四态（已官方核验 / 待核验 / 到期需复核 / 无法核验）、官方核验日期、来源链接、影响条文范围，以及“强制性国标 3 个月、推荐性 / 产品 / 地方 6 个月”的到期周期——与 WorkBuddy 的 citation-discipline 四态高度同构。问题不在设计，而在它停在纸面、没接到生效路径：

  • 没有机械触发：到期规则写在文档里，靠人记得复核——正是“条文存在≠机制生效”。三家都缺同一个东西：一个活的触发器。WorkBuddy 定义了同构四态却未机械校验到期（W-04 中复核周期与自定规则不符却未被门禁拦下即为旁证）；Codex 诚实把全部来源标为“未核验”、日期留空，但没有任何维护闭环（C-02）。
  • 运行时不消费：SRE 只读主索引表的“状态”列，未知编号还默认“现行有效”（Q-01 / Q-02）；它根本不读“核验状态 / 官方核验日期”，四态降级规则没有到达输出。
  • 逐条时效未闭合：主索引表（§二）没有逐条核验日期列，核验记录另在一张表，未与推理链打通。

所以本项目的“自我进化”不是造新概念，而是把已有的四态 / 时效纪律从“定义”接到“机械触发 → 运行时消费 → 缺口回流”。

安全演进闭环：自动化只放检测端，裁定端保持过门

检测（自动 · 确定性）→ 提出（LLM 可草拟候选）→ 核验（过门 · 回读原件）→ 受控入库 → 回测（回归 / 评测）→ 退役（废止 · 到期退出）

检测信号应尽量骑现有门禁（validate_governance、ACE / SRE / IC-07 回归），而不是新建常驻服务或 daemon——避免脚本治理膨胀与空转。LLM 可在“提出”环节草拟候选判据、标出冲突、整理新条文，但产物一律是“候选”，落在包外派生区，不过门不进运行时。这套环与你已有的 agent-wiki 技能（Ingest / Lint / 蒸馏卡 / 回测）是同一骨架，标准领域只需额外挂上生命周期层。
