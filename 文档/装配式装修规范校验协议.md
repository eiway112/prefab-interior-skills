## 装配式装修规范校验协议

_基于 Superpowers 6.0 Review 机制改编，适配装配式装修部品系统方案校验场景。_

---

### 一、核心原则

Superpowers 6.0 发现了一个关键问题：Agent 在长任务里自己写方案、自己解释、自己说"没问题"——这是虚假闭环。装配式装修领域这个问题更危险，因为错误的隔声指标、耐火等级或标高数据直接影响工程质量和验收。

本协议建立四条硬规则：

1. **方案者不能替校验者下结论。** 提出隔墙方案的 Agent 不能在方案里写"经校验，隔声满足要求"——校验结论只能由独立的校验角色给出。
2. **校验者只读不改、只认标准不认解释。** 方案者写的"选用这个构造是因为……"对校验者来说是参考信息，不是校验依据。校验依据只有规范条文、检测报告和计算书。
3. **文件交接，不靠对话传递。** 部品系统的技术参数、接口条件、校验结论全部走结构化文件，不从聊天记录里提取——避免长对话中数据失真。
4. **校验结论锚定到具体条文。** 每条 finding 必须标注所依据的标准编号和条款号，不能写"一般满足"或"基本符合"。

---

### 二、角色定义

#### 2.1 方案 Agent（Implementer）

职责：根据项目约束和用户需求，输出部品系统技术方案。

输出物：`方案提交单`（结构化文件，见第三节模板）。

禁止行为：

- 不得在方案中预写校验结论（如"各项指标均满足规范要求"）
- 不得在校验前声明"可忽略的偏差"（如"隔声差 1-2dB 可接受"）
- 不得在校验过程中修改已提交的方案参数（除非校验报告要求整改）

#### 2.2 校验 Agent（Reviewer）

职责：独立校验方案是否符合规范标准、项目约束和跨部品接口要求。

输出物：`校验报告`（结构化文件，见第三节模板）。

行为规则：

- 只读方案提交单，不修改方案内容
- 对方案者的设计理由保持"参考但不采信"态度
- 每条 finding 必须引用标准编号+条款号，或标注为推断/待确认
- 不得因为方案者的解释而降低严重性等级
- 校验完成后输出 pass / conditional-pass / fail 三级结论

#### 2.3 协调 Agent（Controller，可选）

职责：在复杂项目中协调多个部品系统的方案生成顺序、管理全局约束、分发校验任务。

行为规则：

- 可以向校验 Agent 提供项目约束（抗震等级、造价上限、甲方品牌清单）
- **不得**提前告诉校验 Agent 忽略什么
- **不得**预设校验结论或压低严重性
- 负责将校验报告中的 fail/conditional-pass 项回传给方案 Agent 整改

### 三、文件交接模板

#### 3.1 方案提交单

方案 Agent 完成方案后输出此文件，作为校验 Agent 的唯一输入。

```
# 方案提交单

## 基本信息
- 部品系统：[隔墙/吊顶/楼地面/墙面/厨卫/收纳]
- 项目名称：
- 适用空间：[住宅/酒店/医院/学校/办公/商业]
- 方案版本：v1.0
- 提交时间：

## 项目约束（从任务说明中提取，方案Agent不得自行修改）
- 抗震设防：
- 耐火等级要求：
- 隔声指标要求：
- 造价区间：
- 甲方指定品牌/产品范围：
- 其他限制条件：

## 技术参数
| 指标项 | 设计值 | 选用依据（标准/产品/经验） |
|--------|--------|--------------------------|
| 隔声量 Rw | | |
| 耐火极限 | | |
| 系统厚度 | | |
| 系统重量 | | |
| 抗震性能 | | |

## 构造做法
（分层构造描述，含材料、厚度、连接方式）

## 接口参数
| 接口方向 | 对接部品 | 传递参数 | 接口条件 |
|----------|----------|----------|----------|
| 向上 | 吊顶系统 | 顶标高、龙骨间距、吊点荷载 | |
| 向下 | 楼地面系统 | 底标高、踢脚做法、地面荷载 | |
| 侧面 | 机电管线 | 管线穿越点位、检修口位置 | |

## 方案者备注
（设计理由、已知局限、需要校验者特别关注的事项）
注意：此处的设计理由仅供校验者参考，不构成校验依据。
```

#### 3.2 校验报告

校验 Agent 独立输出此文件，不得修改方案提交单。

```
# 校验报告

## 基本信息
- 方案提交单版本：
- 校验时间：
- 校验依据标准版本：

## 校验结论：[pass / conditional-pass / fail]

## Finding 清单

### Finding #1
- 检查项：[指标名称]
- 方案值：[方案提交单中的设计值]
- 标准值：[规范要求的指标值]
- 判定：[pass / warning / fail]
- 依据：[GB/T XXXXX-XXXX 第X.X.X条]
- 置信度：[S1规范原文 / S2产品检测 / S3经验常数 / S4估算]
- 备注：

### Finding #2
（同上格式）

## 跨部品接口冲突检查
| 冲突项 | 涉及部品 | 冲突描述 | 严重性 | 建议处理 |
|--------|----------|----------|--------|----------|

## 校验者总结
（整体评价、关键风险提示、需要方案者整改的具体项目）
```

#### 3.3 整改回复单（循环使用）

方案 Agent 针对校验报告中的 fail/conditional-pass 项输出整改回复。

```
# 整改回复单

## 针对校验报告版本：

## 整改项

### Finding #X（原判定：fail）
- 原因分析：
- 修改内容：
- 修改后的参数值：
- 是否引入新的接口冲突：[是/否，若是则说明]

### Finding #Y（原判定：conditional-pass）
- 补充说明或修改内容：
```

整改后校验 Agent 对修改项重新校验，输出补充校验报告。循环直到全部 pass 或明确标记为"待专业确认"。

### 四、校验规则

#### 4.1 独立性规则

- 校验 Agent 的校验过程不得引用方案 Agent 在同一会话中的口头解释
- 如果方案提交单中"方案者备注"包含关键设计理由，校验 Agent 应在 finding 中标注"方案者声称[理由]，但标准[编号]要求[规定]，两者[一致/不一致]"
- 协调 Agent 分发校验任务时，只传递方案提交单和项目约束，不传递方案 Agent 的对话记录

#### 4.2 标准锚定规则

- 每条 finding 的"依据"字段不得为空
- 置信度分级：
  - **S1**：国标/行标原文（GB、GB/T、JC/T、JGJ 等），可直接引用
  - **S2**：产品检测报告（CMA/CNAS 认证实验室出具）
  - **S3**：行业经验常数（需标注来源，如"行业通用做法"）
  - **S4**：估算或推断（必须标注"待专业确认"，不得作为 pass 的唯一依据）
- 涉及工程安全、防火、结构性能的 finding，置信度必须达到 S1 或 S2，否则判定为 fail 并标注"数据不足以校验"

#### 4.3 跨部品冲突规则

- 校验 Agent 在校验单部品方案时，必须检查接口参数与已知相邻部品的兼容性
- 典型冲突检查项：
  - 标高链：吊顶底标高 → 隔墙顶标高 → 楼地面完成面标高 → 净高是否满足
  - 荷载链：吊顶荷载 → 隔墙龙骨承载 → 楼板荷载 → 是否在允许范围内
  - 管线穿越：机电管线穿越隔墙/吊顶/楼地面时，开孔尺寸和封堵做法是否满足隔声和耐火要求
  - 工序冲突：相邻部品的安装顺序是否导致无法施工或破坏已完工序
- 冲突严重性分级：
  - **critical**：违反强制性规范或导致无法施工 → fail
  - **major**：影响使用功能或耐久性 → conditional-pass
  - **minor**：优化建议，不影响安全和功能 → pass + warning

#### 4.4 校验结论判定规则

- **pass**：所有 finding 均为 pass 或 warning，无跨部品 critical/major 冲突
- **conditional-pass**：存在 warning 或 minor 冲突，但无 fail 项；需方案者补充说明或微调
- **fail**：存在任何 fail 项或 critical 冲突；方案必须整改后重新提交

### 五、QoderWork 实操工作流

以下是基于本协议在 QoderWork 中的推荐操作流程。

#### 5.1 单部品校验流程

```
步骤1：用户提出需求
  ↓
步骤2：方案Agent（如 prefab-partition-wall-solution）生成方案
  ↓
步骤3：方案Agent输出「方案提交单」文件
  ↓
步骤4：校验Agent（prefab-standards-reviewer）读取方案提交单
  ↓
步骤5：校验Agent独立校验，输出「校验报告」文件
  ↓
步骤6（若 fail/conditional-pass）：方案Agent读取校验报告，输出「整改回复单」
  ↓
步骤7：校验Agent重新校验修改项，输出补充校验报告
  ↓
步骤8：循环直到 pass 或标注"待专业确认"
```

#### 5.2 多部品协同校验流程

适用于完整装配式装修方案（隔墙+吊顶+楼地面+墙面+厨卫等）。

```
步骤1：协调Agent读取项目全局约束，生成「全局约束文件」
  ↓
步骤2：按依赖顺序依次生成各部品方案（建议顺序：隔墙→楼地面→吊顶→墙面→厨卫→收纳）
  ↓
步骤3：每个部品方案完成后，输出方案提交单，进入单部品校验流程
  ↓
步骤4：所有部品方案通过单部品校验后，校验Agent执行「跨部品集成校验」
  - 检查标高链、荷载链、管线穿越、工序顺序
  - 输出「集成校验报告」
  ↓
步骤5（若有冲突）：协调Agent将冲突项分发给相关部品的方案Agent
  - 方案Agent输出整改回复单
  - 校验Agent重新校验
  ↓
步骤6：集成校验 pass，输出最终方案包
```

#### 5.3 操作要点

- **方案提交单和校验报告必须作为文件保存**，不只在对话中展示。建议存放在项目目录的 `校验记录/` 子目录下。
- **校验Agent 的 prompt 中明确写入本协议第四条规则**，确保每次校验都遵循独立性、标准锚定和置信度分级。
- **对话中只展示校验结论和关键 finding**，完整校验过程通过文件查看。避免长对话中数据失真。
- **项目全局约束在任务开始前由用户确认**，协调 Agent 不得自行修改。

### 七、本协议与 Superpowers 的映射

| Superpowers 机制 | 本协议对应 | 适配说明 |
|-----------------|-----------|----------|
| task-reviewer-prompt.md | 校验Agent prompt + 本协议规则 | 单次校验同时覆盖规范符合性和方案质量 |
| Global Constraints | 项目全局约束文件 | 抗震、耐火、造价、品牌等项目级约束 |
| Interfaces | 方案提交单中的接口参数表 | 部品系统间的输入输出关系 |
| 文件交接 | 方案提交单→校验报告→整改回复单 | 替代对话传递，防止数据失真 |
| controller不得提前压掉finding | 协调Agent不得提前告知校验Agent忽略什么 | 防止方案侧话术影响校验独立性 |
| dispatch必须写模型 | 校验Agent prompt中写明校验标准版本 | 确保校验依据明确、可追溯 |
| SDD review合并 | 校验Agent同时做规范校验+方案质量评价 | 减少多轮校验的token消耗 |
